## Historia de usuario

**Como** supervisor, **quiero** que el triaje siga funcionando aunque la API de Anthropic falle, se sature o se quede sin cuota, **para** que ningún ticket quede sin clasificar.

## Contexto

- **Caso de uso:** CU-03
- **Reglas de negocio:** RN-06
- **Servicio:** `servicio-agente-triaje` (`AnthropicClient` + Resilience4j)
- **Endpoint:** `GET /api/v1/triaje/proveedor`

## Criterios de aceptación

- [ ] **Dado** un *timeout* o un error de conexión con Anthropic, **cuando** llega un ticket, **entonces** se reintenta la llamada según la política de `Resilience4j` (número de intentos y espera configurables).
- [ ] **Dados** varios fallos seguidos, **cuando** se supera el umbral, **entonces** el circuit breaker pasa a `OPEN` y las peticiones dejan de llamar a la API durante la espera configurada; después pasa a `HALF_OPEN` para probar de nuevo.
- [ ] **Dado** un error `401`/`403` de Anthropic, **entonces** el circuito se abre sin reintentos (error no transitorio); los errores `429`/`5xx` se tratan como temporales y sí se reintentan.
- [ ] **Dado** que el circuito está `OPEN` o que los reintentos se agotan, **cuando** se procesa el ticket, **entonces** se clasifica por reglas de palabras clave y pasa a `EN_ATTENTE_DE_TRI`.
- [ ] El *timeout*, el número de reintentos y el umbral del circuit breaker se leen del Config Server y se cambian sin recompilar.
- [ ] `GET /api/v1/triaje/proveedor` muestra el estado del circuito (`CLOSED`/`OPEN`/`HALF_OPEN`) y la tasa de fallos.
- [ ] La clave de Anthropic se lee de una variable de entorno y nunca aparece en el repositorio.
